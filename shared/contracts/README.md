# DLA contracts: Interfaces A to D

The data contracts between **Aleeza's side** (desktop agent) and **Fatima's side** (backend, analytics, dashboard). Each contract is a JSON Schema (draft 2020-12) plus sample payloads, and a test checks them.

**Status: v1 draft for Fatima to review.** Everything the spec defines is taken from [docs/](../../docs/). Everything the spec does not define is marked **OPEN QUESTION** (`OQ-...`) in the schema (key `x-open-question`) and in the list at the end of this file. Where a value is a proposal, it says so. The labels "Interface A to D" come from the team plan and [website-activation.md](../../docs/decisions/website-activation.md), not from the spec files.

| | Interface | Direction | Spec source |
|---|---|---|---|
| **A** | Summary upload | agent to backend | FR-9, FR-10, FR-13, "What We Store" (Activity summaries) |
| **B** | Forecast feed | backend to agent | FR-20, FR-21, FR-15, risks table |
| **C** | Settings and corrections | both ways | FR-28, FR-8, FR-4, FR-3, FR-21, "What We Store" (Rules, Goal, Account + settings) |
| **D** | Device activation | both ways (request and response) | decision note website-activation.md |

Run the tests (from this folder):

```bash
pip install -r requirements.txt
python -m unittest discover -s tests -v
```

## Rules that apply to every interface

- **Transport:** HTTPS (TLS) only. The agent sends `Authorization: Bearer <device_token>` (token from Interface D) on A, B and C. Routes and status codes below are **illustrative** (OQ-G1); Fatima owns the API design, these schemas own the payloads.
- **Versioning rule:** the major version is in the file name and in `schema_version` (for example `interface-a.v1`). Every schema is closed (`additionalProperties: false`), so **any** change, even adding one optional field, is a new version (`v2`), published as a new file next to `v1`. A producer never sends a version the consumer has not announced it supports. How long the backend keeps accepting an old version is OQ-G3. Both sides update the schema, the samples and the tests in the same pull request.
- **Time:** UTC, RFC 3339, `Z` suffix. Hour buckets start exactly on the hour. Local time is derived from an explicit offset or IANA zone.
- **IDs:** lowercase UUIDs generated by the sender.
- **Never in any payload:** the user's password, the activation code or device token in a log, keystrokes, screenshots, OCR text, raw events. Consent state is local and is never synced.
- **Privacy is enforced in three places:** the agent validates before sending, the schema is closed so unknown fields fail, and the backend must validate after decrypting and reject (not store) anything that does not match (OQ-G3).

## Interface A: summary upload (agent to backend)

Files: [interface-a.v1.schema.json](schemas/interface-a.v1.schema.json) (the plaintext summary document) and [interface-a-envelope.v1.schema.json](schemas/interface-a-envelope.v1.schema.json) (what is encrypted and sent). Samples: `samples/interface-a.v1.*.json`, `samples/interface-a-envelope.v1.*.json`.

- **Purpose:** give the backend what it needs for reports, score, best hours and the forecast, without any raw activity. FR-9: "Sync encrypted summaries. Works offline; no duplicates. Raw events stay local."
- **Direction:** agent to backend. **Producer:** agent (built from the local SQLite events). **Consumer:** backend and analysis engine.
- **Content (per completed hour):** seconds and mean confidence for each of the five categories (Study, Work, Entertainment, Social Media, Other), seconds marked `unknown`, app/tab switches, interruptions, optional goal-match percent, the user's UTC offset, and a revision number. Nothing else.
- **Encryption:** the document is encrypted into an envelope (`alg`, `key_id`, `nonce`, `ciphertext`). The same envelope bytes are what the agent keeps in its `upload_queue` while offline. The algorithm, who holds the key and how it is delivered are **not defined by the spec** (OQ-A1); AES-256-GCM is a proposal. Note the server must be able to read the summaries (it computes score and forecast), so this is encryption in transit and at rest plus a key the server holds, not a scheme the server cannot open.
- **Idempotency:** `batch_id` (UUID, created once per batch and reused on every retry, also sent as the `Idempotency-Key` header). Sending the same batch again returns success and changes nothing. Inside a batch each hour is identified by `(device_id, hour_start)` and carries a `revision`: the server keeps the highest revision and ignores equal or lower ones. Corrections applied to the past (FR-8) raise the revision of the affected hours and are re-uploaded (OQ-A3). `hour_start` must be unique inside one batch.
- **Retry rule (proposal):** the batch stays in the local queue until the server answers success. On a network error, 429 or 5xx the agent retries with growing delays (for example 1 min, 2, 4, up to 6 h) and never drops the batch for being old. On 400 (the document failed validation) it does **not** retry, it logs a counter (no content) and quarantines the batch. On 401 with `device_revoked` it stops uploading and asks to activate again. Illustrative route: `POST /v1/summaries`; 200 for already-seen, 202 for newly accepted.
- **Receiver checks the schema cannot express:** the five category seconds plus `unknown_seconds` must not exceed 3600 for an hour; `hour_start` unique in the batch; `device_id` equals the token's device.
- **What is NEVER allowed in the payload (privacy):** window titles, URLs, site or domain names, app or process names, page text, OCR text, screenshots or any image, keystrokes or typed text, clipboard, raw events, per-event timestamps. The schema is closed everywhere and contains no free-text string; `tests/test_contracts.py` fails if a schema gains any field that could carry them, and tries 17 forbidden field names at four depths.
- **Consequence for the forecast (OQ-A7, DECIDED):** FR-20 lists "current and previous app" and "session length" as model inputs. App names are raw data and stay on the device, so the forecast uses **category-level data only**: previous category, hour of day, weekday, switches and interruptions. Interface A v1 needs no new field for this: the previous category is the dominant category of the previous hourly summary, and hour of day and weekday come from `hour_start` plus `utc_offset_minutes`. "Session length" has no category-level equivalent in v1.

## Interface B: forecast feed (backend to agent)

File: [interface-b.v1.schema.json](schemas/interface-b.v1.schema.json). Samples: `samples/interface-b.v1.*.json` (including `valid.insufficient-data`).

- **Purpose:** let the agent show nudges ("about 5 minutes before a predicted high-risk window", FR-21) **without internet**. The agent caches the newest valid feed and nudges from it until `valid_until`.
- **Direction:** backend to agent. **Producer:** analysis engine (trains per user, nightly). **Consumer:** agent (nudges); the dashboard reads the same forecast from the backend, not through this contract.
- **Content:** today's hourly `risk` (0 to 1), `confidence`, and a `high_risk` flag; the local `forecast_date` and IANA `timezone`; model version; `source` (personal model or smart defaults); optional best focus windows (weekday/weekend) for the "suggested focus block".
- **Before day 14:** `status: insufficient_data` with `days_of_data` and no hours. The agent shows no forecast and sends no nudge.
- **Versioning:** as above. **Caching / retry rule (proposal):** the agent keeps the last valid feed on disk and replaces it only with a higher `feed_version`. It polls (for example hourly and at start-up) with `If-None-Match: <feed_version>`; a 304 or a network failure keeps the cache. Expired feed means no nudges (OQ-B3). Illustrative route: `GET /v1/forecast`.
- **Never allowed in the payload:** anything about what the user did (no titles, URLs, apps), user-visible account data, and any nudge limit. Nudge limits (2 per day, cooldown, off after 2 ignores) are decided on the PC, not here.

## Interface C: settings and corrections (both directions)

File: [interface-c.v1.schema.json](schemas/interface-c.v1.schema.json). Samples: `samples/interface-c.v1.*.json`.

- **Purpose:** keep the user's choices identical on the PC and on the dashboard: retention days, idle threshold, pause, hidden apps and sites, nudge on/off and snooze, the daily goal, **personal rules** (corrections, FR-8), and **delete by date or all** requests (FR-28). Also carries the website terms version and accepted-at from the server (decision note).
- **Direction:** both. **Producer:** whichever side the user changed (`updated_by`). **Consumer:** the other side.
- **Not in this contract:** the **consent record**. Consent is local and the source of truth for recording; it is never synced (decision note). OCR per-app opt-in is also not synced (OQ-C4, DECIDED: local-only).
- **Pause rule (OQ-C3, DECIDED):** the dashboard may set `paused` to true; it may **not** set it back to false. Only the user at the PC can resume. If the agent receives a document from the dashboard with `paused: false` while the PC is paused, it ignores that value, stays paused, and writes its own newer revision so the dashboard sees the real state.
- **Idempotency / retry rule (proposal):** one document with a `revision` counter. A writer sends `PUT` with `If-Match: <revision it last saw>`; the receiver accepts it only if that is still the latest and then increments the revision; on a mismatch (409) the writer re-reads, merges (rules by `rule_id` and `updated_at`, newest wins; other settings newest `updated_at` wins) and sends again. Re-sending the same document is harmless. Deleted rules remain as tombstones (`deleted: true`) so deletions propagate. Retries use the same backoff as Interface A. Illustrative routes: `GET` and `PUT /v1/settings`. All of this is OQ-C1.
- **Delete requests:** each has a `request_id`; applying one twice is harmless. The agent deletes local raw events and summaries in range; the backend deletes its summaries for the range; the receiving side confirms by removing the request from the document once done (OQ-C6).
- **Never allowed in the payload:** raw events, titles or URLs as data, screenshots, OCR text, consent state, keystrokes. The only user-chosen text is rule `pattern`, excluded app/site names and the goal text (max 280 characters). `title_contains` patterns and exclusion lists can themselves be sensitive, so they are marked OQ-C2 and the dashboard must treat them as private.

## Interface D: device activation (`dla://activate`)

File: [interface-d.v1.schema.json](schemas/interface-d.v1.schema.json) (three message types in one file). Samples: `samples/interface-d.v1.*.json` (`valid` = request, `valid.response`, `valid.error`).

- **Purpose:** link the desktop agent to the user's account **without a password in the agent**. After sign-up and accepting the website terms, the website shows a button that opens `dla://activate?code=<one-time code>`. Windows passes the link to the agent (registered per user in HKCU, no admin rights). The agent posts the code and receives a **revocable per-device token** and its `device_id`. Then the agent shows the existing **local consent screen**; nothing is recorded until the user accepts there.
- **Direction:** agent to backend (`activation_request`), backend to agent (`activation_response` or `error`). **Producer of the code:** website/backend. **Consumer:** agent. **Link format:** exactly `dla://activate?code=<code>`; the agent rejects any other host, path or extra parameter.
- **Idempotency / retry rule:** the code is **single use**: a second attempt returns `code_used`. If the response is lost after the server consumed the code, the agent cannot recover it; the user clicks the website button again to get a new code. The agent retries only on network failure, never after an `error` response, and honors `retry_after_seconds`. Code format and lifetime are OQ-D1. Illustrative route: `POST /v1/devices/activate`.
- **Revocation:** the website's device list can revoke a device. Afterwards A, B and C answer 401 with `{"message_type":"error","error":"device_revoked"}`; the agent stops uploading and asks the user to activate again. The token is stored protected by Windows (DPAPI, current user).
- **Never allowed in the payload:** a password or any credential other than the one-time code, the website session cookie, payment data. The code and the token must **never be logged**, written to a file in the repo or put in a crash report. `device_name` is optional (OQ-D2).

## Open questions for Fatima

Everything below is either not defined by the spec or a proposal in the schemas that needs your decision. IDs match the `x-open-question` keys in the schemas.

**General**
- **OQ-G1:** Route names, HTTP status codes and error bodies for A, B, C. The README shows illustrations only.
- **OQ-G2:** Rate limits and maximum request sizes for each route.
- **OQ-G3:** How long does the backend accept an older `schema_version` after a new one ships, and will it reject and not store any payload with an unknown field (the privacy backstop)?

**Interface A (summaries)**
- **OQ-A1:** What does "encrypted summaries" mean exactly: which algorithm, who generates and holds the key, how it reaches the agent (at activation?), how keys rotate, and what the authenticated additional data covers. AES-256-GCM with a per-device key issued by the server is only a proposal.
- **OQ-A2:** Is `utc_offset_minutes` per hour the right way to give the server local hour-of-day and weekday/weekend (FR-15, FR-20)?
- **OQ-A3:** Is the per-hour `revision` rule right ("highest revision wins")? Should the agent upload an hour only when it is complete, and how does a correction applied to the past re-upload affected hours?
- **OQ-A4:** `goal_match_percent`: should the agent compute the semantic match (it has the titles) or should the server (it has only summaries)? Per hour is a proposal.
- **OQ-A5:** Limits: hours per batch (744 = 31 days proposed) and maximum ciphertext size (about 2 MB proposed).
- **OQ-A6:** What counts as a "switch" and as an "interruption" for FR-13? The spec does not define either.
- **OQ-A7:** **DECIDED 2026-10-09 (Aleeza).** FR-20 uses "current and previous app" and "session length", but app names are raw data and stay on the device. Forecast features use category-level data only: previous category, hour of day, weekday, switches, interruptions. Reasoning: it keeps the spec's promise that raw events (which include the app) never leave the PC, and the contract needs no new field. App-level features may be added later only as an **explicit opt-in** (a new schema version, with its own consent text). Fatima: train and validate the 60% precision target (FR-20) on these features.
- **OQ-A8:** How is hourly `confidence` per category averaged (by seconds? by event?), and is that the number the Needs Review rule and the dashboard should show?

**Interface B (forecast feed)**
- **OQ-B1:** Do "smart defaults" (aggregated patterns for new users) arrive through this feed, and from which day?
- **OQ-B2:** Who proposes the "suggested focus block" in a nudge (FR-21): the backend through `focus_windows`, or the agent from the forecast?
- **OQ-B3:** Feed lifetime (`valid_until`) and what the agent does when it expires while offline (stop nudging?).
- **OQ-B4:** Horizon: today only, or also tomorrow? DST days have 23 or 25 hours (the schema allows 25).
- **OQ-B5:** The nudge success measure (users acting on a nudge: dismiss, snooze, accept, at least 30%) needs those actions reported somewhere. No interface carries them today. Should it be a field in A, or a new interface?
- **OQ-B6:** Who owns the `high_risk` threshold (the flag that FR-20's 60% precision is measured on)?

**Interface C (settings and corrections)**
- **OQ-C1:** Conflict handling: is the single `revision` plus `If-Match` plus newest-wins merge acceptable?
- **OQ-C2:** Rule `pattern` values (especially `title_contains`) and the hidden app/site lists are user content that may be sensitive, yet "Rules" are listed as cloud data. Confirm they are stored encrypted and may be read by the dashboard only for the owner.
- **OQ-C3:** **DECIDED 2026-10-09 (Aleeza).** The dashboard may pause tracking remotely but may not resume it; only the user at the PC can resume. Reasoning: pausing is always the privacy-safe direction, while a remote resume would start recording on a PC without the person there, which conflicts with "nothing is recorded without local consent". Rule and conflict handling are written in the Interface C section.
- **OQ-C4:** **DECIDED 2026-10-09 (Aleeza).** OCR opt-in settings are not synced; they stay local-only. Reasoning: which apps a person allows screen-reading for is sensitive, the OCR feature never leaves the device by spec, and the dashboard has no need for it. Interface C therefore has no OCR field.
- **OQ-C5:** Allowed ranges: retention 1 to 3650 days and idle threshold 30 to 3600 seconds are the agent's current choices, not the spec's.
- **OQ-C6:** Delete semantics: does "delete everything" also remove the cloud copy of rules and settings, and how does the dashboard learn that the PC finished deleting? What does "export data" (FR-28) return, and is it produced by the agent, the backend, or both?
- **OQ-C7:** The "auto-suggested goal from history" (quality table): produced by the agent or the backend?

**Interface D (activation)**
- **OQ-D1:** Code format, length and lifetime (proposal: 16 to 128 URL-safe characters, single use, minutes).
- **OQ-D2:** Collect `device_name` for the device list? A PC name can identify a person.
- **OQ-D3:** Token lifetime, rotation and refresh; how the agent learns a token was revoked while offline.
- **OQ-D4:** One agent per account, or several PCs? What happens if a second activation arrives on a PC that is already linked (replace, or refuse)?
- **OQ-D5:** Sign-out or unlink from the agent side: is there an interface for it?
- **OQ-D6:** Where does the website send the user if the agent is not installed yet (installer download, then the activation link)?
